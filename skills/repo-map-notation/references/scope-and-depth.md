# scope-and-depth — 範囲と深度の選び方

`repo-map v1` で巨大リポジトリを扱う鍵は、**一度に全部描こうとしないこと**。範囲（`@meta root`）と深度（`@meta depth`）の 2 軸で、読める大きさに切り出す。文法は [grammar.md](grammar.md)。

---

## 2 つの軸

- **範囲（root）** — 地図の起点。`.` ならリポジトリ全体、`apps/web` ならその部分木だけ。**狭めるほど**詳細を入れても上限（ノード ≤ 40 等）に収まる。
- **深度（depth）** — 粒度。0 / 1 / 2 の 3 段階。**深くするほど**細かいノード種別を使う。

原則: **「全体を深く」ではなく「範囲を狭めて深く」**。深掘りは root を下げて行う。

---

## depth の定義

### depth 0 — システム
リポジトリ（または製品）を、数個の粗い塊として描く。主に `system`・`external`・`datastore`。
- 使う種別: system / external / datastore（package は避ける）
- 目安ノード数: 3〜10
- 問い: 「このシステムは、外から見て何と何でできているか」

### depth 1 — パッケージ／トップ階層
トップレベルのディレクトリやパッケージを 1 ノードにし、その間の主要な依存を描く。最も使う深度。
- 使う種別: package 中心（＋ external / datastore）
- 目安ノード数: 6〜25
- 問い: 「どのパッケージがあり、何に依存するか」

### depth 2 — 主要ファイル群
**範囲を 1 パッケージ程度に絞った上で**、その内部を module / file-group の粒度で描く。
- 使う種別: module / file-group（＋ external / datastore）
- 目安ノード数: 6〜30（ただし範囲を絞っているので収まる）
- 問い: 「この 1 つのパッケージは、内部でどう組み立っているか」

> depth と種別の整合は検証される（[grammar.md](grammar.md) の W-DEPTHEXCEED）。depth 0 に module を混ぜると警告になる。

---

## 選び方フロー

1. **目的を 1 文にする**（STEP 0 の「何が分かれば成功か」）。
2. その文が「システム全体の関係」なら depth 0、「主要コンポーネントと依存」なら depth 1、「ある部分の内部」なら**範囲を絞って** depth 2。
3. 出力が上限に近づいたら、**深度を下げる**か**範囲を狭める**。決して箱を増やして押し込まない。
4. 「ここを詳しく」と言われたら、その部分に root を下げ、depth を 1 段上げて作り直す（全量・部分スコープ）。

---

## リポジトリ類型別ガイド

### モノレポ（apps/ と packages/ が同居）
- **入口は depth 1、root は `.`**。トップの `apps/*` と `packages/*` を package ノードにし、`contains` で束ね、アプリ → 共有パッケージの `imports` を引く。
- 共有コア（多くが依存する package）に `focus` を当てると、依存の収束が一目で分かる。
- アプリ 1 つの内部を見たいときだけ、root を `apps/web` に下げて depth 2。

### マイクロサービス（サービスごとに独立、ネットワーク越し）
- **depth 1、各サービスを package**（またはサービス境界として system）に。サービス間は同期呼び出しなら `calls`、データ参照なら `reads`。
- インフラ境界を `external`（外部 API・SaaS）と `datastore`（各サービスの DB・キュー・キャッシュ）で明示する。「どのサービスがどの datastore を読むか」が地図の主役になりやすい。
- デプロイ単位を見せたいときは `deploys`（例: `system deploys service`）。

### レガシー巨大単一リポジトリ（階層が深い 1 つの塊）
- いきなり depth 1 で全体を出すと上限を超えがち。まず **depth 0** で「外から見た塊」を数個に割り、塊ごとに範囲を絞って depth 1〜2 に降りる。
- 自然な package 境界（ビルド定義ファイル）が乏しい場合は、トップの主要ディレクトリを暫定の package ノードと見なし、`contains` で粗く束ねる。
- 「読みたい 1 機能」から逆に範囲を決める（機能のエントリポイントを root に近い位置で押さえ、そこからの依存だけを depth 2 で追う）。

## よくある失敗と対処

| 失敗 | 兆候 | 対処 |
|------|------|------|
| 1 枚で全部描こうとする | ノード > 40、エッジ > 80 | 範囲を狭める／深度を下げる／近いノードをグルーピング |
| file 単位で並べてしまう | file-group/module が大量、depth 1 なのに細かい | package/module に抽象化、深掘りは範囲を絞ってから |
| 依存を全部引く | エッジが毛玉 | 代表的・構造を語る依存だけ残す（網羅しない） |
| レイアウトを意味に混ぜる | `@nodes` に位置、`@layout` に種別 | 意味は @nodes/@edges、位置は @layout に分離 |
